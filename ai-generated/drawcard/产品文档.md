# 抽牌游戏产品文档

## 1. 产品概述

### 1.1 游戏简介
抽牌游戏是一款基于风险与收益的多人在线卡牌游戏。这是一个**零和博弈**系统，玩家通过竞拍成为地主或农民，农民通过抽牌获取价值，但面临炸弹风险。游戏融合了策略、运气和心理博弈元素，所有收益来源于玩家间的财富重新分配。

### 1.2 核心玩法
- **4人对战**：固定4人房间，支持实时对战
- **角色分化**：地主vs农民，不同的游戏策略
- **风险决策**：每次抽牌都是风险与收益的权衡
- **动态价值**：牌的价值会在游戏过程中发生变化

### 1.3 目标用户
- 喜欢策略类卡牌游戏的玩家
- 享受心理博弈的休闲游戏爱好者
- 寻求快节奏游戏体验的用户（单局15-20分钟）

## 2. 详细游戏规则

### 2.1 游戏初始化
- **玩家数量**：固定4人
- **玩家手牌**：每人初始手牌为0张
- **牌库构建**：每人带入5张牌进入牌库
- **入场费**：每人100积分
- **基础奖池**：入场费之和(400积分)
- **零和机制**：牌库总价值 = 玩家入场费 + 地主竞拍费

### 2.2 地主竞拍阶段
#### 竞拍流程
1. 按照 A → B → C → D → A 的顺序进行5次出价机会
2. 每个玩家轮到时可以选择：
   - 出价（必须高于当前最高价）
   - 放弃竞拍
3. 5次出价机会结束后竞拍结束
4. 最高出价者成为地主，支付出价金额到奖池

#### 竞拍规则
- **出价次数**：固定5次（每人一次，发起者额外一次）
- **最低出价**：10积分
- **出价增量**：最少10积分
- **最高出价**：不限制
- **无地主情况**：如果5次出价机会内无人出价，则本局无地主

### 2.3 牌库构成与价值分配

#### 零和博弈原理
- **资金来源**：玩家入场费(400积分) + 地主竞拍费
- **价值分配**：牌库总价值 = 总资金投入
- **财富转移**：通过抽牌机制重新分配所有投入资金

#### 有地主模式（25张牌）
- **玩家价值牌**：15张，总价值300积分
- **地主炸弹牌**：5张(由地主带入的价值牌转换)
- **系统价值牌**：5张，价值为100积分+地主出价
- **牌库总价值**：400积分 + 地主出价 = 总投入资金

#### 无地主模式（25张牌）
- **玩家价值牌**：20张，总价值400积分
- **系统炸弹牌**：5张
- **牌库总价值**：400积分 = 总投入资金

### 2.4 农民游戏阶段
#### 回合流程
1. **抽牌**：从牌库随机抽取5张牌（背面朝上）
2. **翻牌决策**：选择翻开任意张牌（至少1张）
3. **效果结算**：
   - 价值牌：复制一张该价值牌到玩家手牌，牌库中该牌价值归零
   - 炸弹牌：立即离场，结算手牌中所有价值牌的价值
4. **还牌**：将抽到的牌放回牌库
5. **离场决策**：选择是否主动离场保住当前收益

#### 特殊规则
- **防重复**：玩家不会抽到自己之前抽过的牌
- **最大回合数**：每个农民最多进行5回合
- **强制结束**：所有农民离场后游戏结束

### 2.5 地主游戏阶段
- **观战模式**：地主不参与抽牌，只能观看其他玩家
- **收益计算**：游戏结束后获得牌库中剩余的所有价值牌总和
- **风险**：如果农民获得的总价值超过地主的潜在收益，地主可能亏损

### 2.6 胜负判定

#### 零和博弈结算
所有玩家的净收益总和为零，一方的收益必然来自其他玩家的损失。

#### 积分计算
- **农民**：手牌中价值牌的价值总和 - 入场费
- **地主**：牌库剩余价值 - 入场费 - 竞拍出价

#### 农民手牌机制
- **初始手牌**：0张牌
- **获得方式**：翻开价值牌时获得该牌的复制
- **结算时机**：离场时结算手牌中所有价值牌的价值总和
- **价值来源**：手牌价值牌保持原始价值（不受牌库中该牌价值归零影响）

#### 资金平衡验证
- 总投入 = 4×100(入场费) + 地主出价
- 总分配 = 所有玩家获得的价值牌总和
- 投入 = 分配（零和平衡）

## 3. 技术架构规范

### 3.1 技术栈
- **后端框架**：Node.js + Express.js
- **实时通信**：Socket.IO
- **数据库**：Redis（游戏状态）+ MongoDB（用户数据）
- **前端**：HTML5 + CSS3 + JavaScript（原生或Vue.js）

### 3.2 系统架构
```
客户端 (Web Browser)
    ↓ Socket.IO
游戏服务器 (Node.js)
    ↓
游戏状态管理 (Redis)
用户数据存储 (MongoDB)
```

### 3.3 核心模块设计

#### 3.3.1 房间管理模块
- 房间创建与销毁
- 玩家加入与离开
- 房间状态同步

#### 3.3.2 游戏逻辑模块
- 竞拍逻辑处理
- 抽牌与翻牌逻辑
- 积分计算与结算

#### 3.3.3 牌库管理模块
- 牌库初始化
- 牌的状态追踪
- 防重复抽牌机制

## 4. 数据模型设计

### 4.1 游戏房间模型
```javascript
{
  roomId: String,
  players: [
    {
      playerId: String,
      playerName: String,
      role: String, // 'farmer' | 'landlord'
      score: Number,
      isActive: Boolean,
      drawnCards: [String] // 已抽过的牌ID
    }
  ],
  gameState: String, // 'waiting' | 'bidding' | 'playing' | 'finished'
  currentPlayer: String,
  biddingInfo: {
    currentBid: Number,
    currentBidder: String,
    biddingRound: Number
  },
  cardDeck: [
    {
      cardId: String,
      type: String, // 'value' | 'bomb' | 'system_value' | 'system_bomb'
      value: Number,
      isActive: Boolean
    }
  ],
  roundCount: Number,
  createdAt: Date,
  updatedAt: Date
}
```

### 4.2 玩家操作模型
```javascript
{
  action: String, // 'bid' | 'draw' | 'flip' | 'leave'
  playerId: String,
  data: {
    bidAmount: Number, // 竞拍金额
    selectedCards: [String], // 选择翻开的牌
    leaveGame: Boolean // 是否离场
  }
}
```

## 5. API接口设计

### 5.1 RESTful API
```javascript
// 创建房间
POST /api/rooms
Response: { roomId, joinCode }

// 加入房间
POST /api/rooms/:roomId/join
Body: { playerName }
Response: { playerId, gameState }

// 获取房间状态
GET /api/rooms/:roomId
Response: { gameState, players, currentRound }
```

### 5.2 Socket.IO事件
```javascript
// 客户端发送事件
'join-room': { roomId, playerName }
'place-bid': { bidAmount }
'draw-cards': { }
'flip-cards': { cardIds }
'leave-game': { }

// 服务端广播事件
'game-state-update': { gameState, players }
'bidding-update': { currentBid, currentBidder }
'card-drawn': { cards, playerId }
'card-flipped': { cardId, value, effect, playerId }
'player-eliminated': { playerId, reason }
'game-finished': { finalScores, winner }
```

## 8. 技术实现要点

### 8.1 关键算法
- **防重复抽牌**：为每个玩家维护已抽牌记录
- **价值洗牌**：Fisher-Yates算法打乱价值牌价值分配
- **实时同步**：使用Socket.IO确保所有玩家状态一致

### 8.2 性能考虑
- **内存管理**：及时清理结束的游戏房间
- **并发处理**：支持多房间同时进行
- **网络优化**：最小化数据传输量

### 8.3 安全措施
- **操作验证**：服务端验证所有玩家操作的合法性
- **防作弊**：牌库状态仅在服务端维护
- **超时处理**：自动处理掉线和超时情况
